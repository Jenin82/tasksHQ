# Contributing to TasksHQ

Thanks for helping. This guide covers setup, the rules the codebase depends on, the checks to run, and how to send a pull request. [CLAUDE.md](CLAUDE.md) has the full list of repository conventions; read it before larger changes. [PLAN.md](PLAN.md) is the historical design record that source comments cite as "PLAN §…".

## Development setup

Requires Node.js 24 and pnpm 10.25.0. Follow [Run locally](README.md#run-locally) in the README:

```sh
pnpm install --frozen-lockfile
cp deploy.env.example deploy.env          # set TASKSHQ_D1_ID to any UUID for local-only work
cp apps/web/.dev.vars.example apps/web/.dev.vars
cp apps/mcp/.dev.vars.example apps/mcp/.dev.vars
```

Then apply local migrations and run `pnpm dev`. `pnpm --filter web seed [email]` resets a local `acme` organization with sample data. You do not need a Cloudflare account to develop or run tests.

## Rules to follow

- **Every mutation goes through a domain function** in `packages/core/src/domain`, called with `{ db, actorUserId, source: 'web' | 'mcp', ... }`. The domain function checks access and records activity in the same `db.batch` as the write. Do not write SQL in Server Actions, route handlers or MCP tools.
- **Access checks live in the shared domain write**, including bulk actions, so web and MCP enforce the same rules.
- **Schema changes ship as new migrations.** Edit the schema in `packages/core/src/schema`, then generate a migration from `apps/web`:

  ```sh
  cd apps/web
  pnpm exec drizzle-kit generate --name <short_description>
  ```

  This writes `drizzle/NNNN_<name>.sql` and updates `drizzle/meta`. For data-only changes, use `drizzle-kit generate --custom --name <name>` and write the SQL by hand. Commit the SQL and the `meta` files together.
- **Never edit a migration that has been merged.** Deployments have already applied it. Add a new migration instead.
- **Migrations must be safe to apply before either Worker deploys**, because deployments run `pnpm run db:migrate:remote` first. Avoid dropping or renaming columns the current release still reads in the same change.
- **Add dependencies from the repository root** with `pnpm add --filter <package> <dep>`. Do not run `pnpm add` inside an app; it duplicates `drizzle-orm`.
- **Use the `cf` CLI** with `cloudflare.config.ts`, not wrangler. Do not hardcode domains, account IDs or resource IDs; deployment values come from `deploy.env` and `secrets.env`.
- **Keep `prerender` off** in `apps/web/vite.config.ts`. Every route renders authenticated data.
- **Follow `apps/web/design.md`** for visual decisions. PLAN §7 records deviations. Use one blue (`--primary`) call to action per view.

## Checks

Run all of these before opening a pull request. CI runs the same set.

```sh
(cd packages/core && npx tsc --noEmit -p .)
(cd apps/web && pnpm exec cf workers types && npx tsc --noEmit -p .)
(cd apps/mcp && pnpm exec cf workers types && npx tsc --noEmit -p .)
pnpm --filter web test
pnpm --filter mcp test
pnpm --filter web build
```

`cf workers types` generates the Worker `Env` types into `.cloudflare/types` (gitignored). Tests run in workerd through `@cloudflare/vitest-plugin`. Add or update tests for behavior you change, especially access rules and domain functions.

## Pull requests

1. Fork the repository and create a branch from `main`.
2. Keep each pull request small and focused on one change. Separate refactors from behavior changes.
3. Describe what changed and why, and how you tested it. Include screenshots for UI changes.
4. If the change adds a migration, say so in the description, name the file, and note any rollout order (for example, "apply before deploying either Worker").
5. If the change affects deployment, configuration or secrets, update `README.md`, `AGENTS.md` and the `*.example` files.
6. Make sure CI passes.

## Documentation

- The public product guide lives in `apps/web/app/docs`. Each guide's text is in its `content.tsx`, which the docs search also reads. Preserve existing section IDs so links keep working, and add `searchTerms` for common alternate wording.
- Capture docs images with synthetic data only.
- Update `CLAUDE.md` when you introduce a convention other contributors must follow.

## Reporting bugs and requesting features

Open a GitHub issue using the bug report or feature request template. Include steps to reproduce, expected and actual behavior, and whether it happens in the web app, MCP, or both.

Do not report security vulnerabilities in public issues. Follow [SECURITY.md](SECURITY.md).
